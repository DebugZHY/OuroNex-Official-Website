“Scoped” is one of those words that sounds precise and says very little. In our work it means something deliberately small: one workflow, in one team, with the assumptions written down before anything is built.

A scoped pilot starts from a process the firm already runs. We map the steps, the handoffs and the existing checks, then agree which parts AI can assist and which stay with the engineer. The output of scoping is not a plan for a platform. It is a short agreement: what will be tried, how the team itself will judge it, and who reviews each stage.

## What the review gates commit to

Each stage carries its own review gate. The first gate confirms the workflow and the assumptions. The second checks a small, real piece of work against the existing standards. Only then does the pilot move into regular use, and only while review remains active. A gate is not a formality: if the work does not pass, the pilot stops or returns to scope.

> A pilot tests whether one workflow can be trusted on real work. It does not commit the firm to a rollout, and it does not promise that any task will be automated.

It is worth saying what a pilot is not. It is not a platform rollout, and it is not a promise of automation. Some steps may not be suitable for assistance at all, and saying so early is a useful result rather than a failure. The engineer keeps responsibility for every professional decision, whether or not a model was involved.

Practice begins when the workflow has survived that scrutiny and the team can run it without us. Then the same pattern can be scoped again for a second workflow — again with named assumptions, again with staged acceptance. The unit is always the workflow, not the tool.
